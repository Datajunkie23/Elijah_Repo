# 🍕🛢️ Pizzeria Database Design and Implementation Using MySQL

## Project Overview

This project focuses on the design and implementation of a relational database for a takeaway pizzeria using **MySQL**. The objective was to translate a client's business requirements into a well-structured database capable of storing and managing operational data efficiently.

The project began with a project brief outlining the information the client wanted to capture. Based on these requirements, the database schema was planned using an **Entity Relationship Diagram (ERD)** before being implemented in MySQL through the creation of tables, primary keys, foreign keys, unique constraints, and relationships.

Rather than focusing on data analysis, this project demonstrates the foundational stages of database development, including database design, normalization, relational modelling, and schema implementation. The resulting database provides a structured foundation capable of supporting future data analysis, reporting, and business intelligence applications.

## 📌 Project Scenario

A client named **Ben** is preparing to launch a new takeaway pizzeria. Unlike a traditional dine-in restaurant, the business will operate exclusively as a takeaway service. To support the day-to-day operations of the business, Ben requires a custom-built relational database capable of capturing, storing, and organising the information generated by the pizzeria.

The database will serve as the backend data repository for the business, while a separate frontend ordering system will be developed independently. By organising operational data into a structured relational database, Ben will be able to monitor business activities efficiently and establish a reliable foundation for future reporting and analysis.

The project brief focuses on three major business areas:

- **Customer Orders**
- **Stock Control**
- **Staff Management**

To satisfy these requirements, the database was carefully designed by identifying the necessary entities, defining their attributes, establishing relationships between them, and applying database normalization principles to eliminate redundancy and improve data integrity.

# 📦Customer Orders Module

The first requirement outlined in the client's project brief focused on managing customer orders. Since the pizzeria operates exclusively as a takeaway business, the database needed to capture customer information, order details, delivery addresses, and menu items efficiently while minimizing redundant data storage.

To achieve this, the Customer Orders module was designed using four related tables:

- `orders`

- `item`

Instead of storing all information within a single table, the database was normalized by separating related information into dedicated tables and connecting them through foreign key relationships.

# Creating the Orders Table

The **orders** table was the first table created because it represents the central transaction table for the business.

Initially, the table contained all of the information supplied in the project brief, including:

- Order information
- Customer information
- Delivery information
- Item information

Additional columns were also introduced to provide a more comprehensive representation of each order.

The initial attributes included:

- `row_id`
- `order_id`
- `created_at`
- `item_name`
- `item_category`
- `item_size`
- `item_price`
- `quantity`
- `customer_firstname`
- `customer_lastname`
- `delivery`
- `delivery_address1`
- `delivery_address2`
- `delivery_city`
- `delivery_zipcode`

### Why `row_id` Was Used as the Primary Key

Although the table already contained an `order_id` column, it could not be used as the primary key because a single customer order can contain multiple menu items. As a result, multiple rows may share the same `order_id`, making it unsuitable as a unique identifier.

To uniquely identify every record, a new column named **`row_id`** was introduced and designated as the primary key.

# 🔄 Identifying Data Redundancy

After testing the database structure with a sample dataset, it became evident that the Orders table contained significant duplicated information.

For example:

- The same customer information appeared repeatedly.
- Delivery addresses were duplicated across multiple records.
- Menu item information was repeated whenever the same item appeared in different orders.

This duplication increased storage requirements and introduced the possibility of inconsistent data updates.

To address this issue, the orders table was normalized by separating related information into dedicated tables while maintaining relationships through foreign keys.

---

# Creating the Customers Table

The first step in the normalization process was creating the **customers** table.

Rather than storing customer names repeatedly inside every order, customer-related information was moved into a dedicated table.

The table contains:

- `customer_id`
- `customer_first_name`
- `customer_last_name`

After creating the table, the `customer_id` column was designated as the primary key to ensure that it contains no `NULL` values and that every customer has a unique identifier.

A new column named **`cust_id`** was then added to the **orders** table, where it serves as a foreign key referencing the `customer_id` column in the **customers** table.

Once the relationship had been established successfully, the following columns were removed from the **orders** table:

- `customer_firstname`
- `customer_lastname`

This eliminated duplicate customer information while preserving the relationship between customers and their orders.

# Creating the Address Table

The next stage of normalization focused on delivery information.

Originally, every order stored complete delivery address details, including:

- `delivery_address1`
- `delivery_address2`
- `delivery_city`
- `delivery_zipcode`

Since many orders can reference the same delivery location, storing address information repeatedly would introduce unnecessary redundancy.

To solve this, an **address** table was created containing:

- `address_id`
- `delivery_address1`
- `delivery_address2`
- `delivery_city`
- `delivery_zipcode`

The `address_id` column was designated as the primary key.

A new column named **`add_id`** was then added to the **orders** table and linked to the **address** table through a foreign key relationship.

After establishing the relationship, the delivery-related columns were removed from the **orders** table, leaving only the foreign key reference.

This approach significantly reduced duplicated address information while maintaining the relationship between orders and delivery locations.

# Creating the Item Table

The final stage of normalization within the Customer Orders module focused on menu items.

Initially, item-related information such as:

- `item_name`
- `item_category`
- `item_size`
- `item_price`

was stored directly inside the **orders** table.

Since the same menu item can appear across multiple customer orders, storing this information repeatedly would result in unnecessary duplication.

To improve the database design, a dedicated **item** table was created containing:

- `item_id`
- `item_sku`
- `item_name`
- `item_category`
- `item_size`
- `item_price`

The `item_id` column was assigned as the primary key.

A corresponding `item_id` column was then added to the **orders** table, where it serves as a foreign key referencing the **item** table.

After establishing the relationship, all item-related columns were removed from the **orders** table.

The result is a cleaner and more efficient database structure where each menu item is stored only once while remaining accessible through relational links.

# Stock Control Requirements

One of Ben's primary objectives was to determine **when additional stock should be ordered**.

To accomplish this, the database needed to capture information about:

- The ingredients required to prepare each menu item.
- The quantity of each ingredient used within a recipe.
- The current stock levels available in inventory.

---

# Creating the Recipe Table

The first table created within the Stock Control module was the **recipe** table.

This table acts as the bridge between menu items and the ingredients required to prepare them.

The table contains the following attributes:

- `row_id`
- `recipe_id`
- `ing_id`
- `quantity`

The `row_id` column was designated as the primary key to uniquely identify each record within the table.

### Establishing the First Relationship

From the Entity Relationship Diagram (ERD), the `recipe_id` column was identified as a foreign key referencing the `item_sku` column within the **item** table.

Since foreign keys must reference either a **Primary Key** or a **Unique Key**, the `item_sku` column in the **item** table was modified by adding a **Unique** constraint before the relationship was established.

This allowed each recipe to be linked to its corresponding menu item while maintaining referential integrity.

# 🔑 Primary Keys

Every table within the database contains a primary key used to uniquely identify each record.

Primary keys play an essential role by:

- Preventing duplicate records.
- Providing a unique identifier for every row.
- Supporting relationships between tables.
- Maintaining data consistency throughout the database.

The implementation of primary keys ensures that each entity within the database can be uniquely identified and referenced by related tables.

---

# 🔗 Foreign Keys

Relationships between tables were established using foreign keys.

Rather than duplicating information across multiple tables, foreign keys allow related records to reference one another while preserving data integrity.

The primary relationships implemented include:

| Parent Table | Child Table | Relationship |
|--------------|-------------|--------------|
| Customers | Orders | `cust_id → customer_id` |
| Address | Orders | `add_id → address_id` |
| Item | Orders | `item_id → item_id` |
| Item | Recipe | `recipe_id → item_sku` |
| Ingredient | Recipe | `ing_id → ing_id` |
| Inventory | Recipe | `ing_id → item_id` |
| Orders | Rota | `date → created_at` |
| Staff | Rota | `staff_id → staff_id` |
| Shift | Rota | `shift_id → shift_id` |

These relationships allow related business information to remain connected while eliminating unnecessary duplication across the database.

---

# ⭐ Unique Constraints

Several columns were assigned **Unique** constraints before foreign key relationships were established.

These constraints ensure that the referenced columns contain unique values, allowing them to participate in foreign key relationships while preventing duplicate entries.

Examples include:

- `item_sku`
- `inventory.item_id`
- `orders.created_at`

Applying these constraints improves data integrity and ensures that relationships remain valid throughout the database.

---

# Database Normalization

Normalization played a significant role in the overall database design.

The project initially began with a denormalized **orders** table containing customer information, delivery addresses, and menu item details within a single structure.

As development progressed, redundant information was separated into dedicated tables, including:

- Customers
- Address
- Item

This approach significantly reduced duplicated data while improving consistency, scalability, and maintainability.

Instead of storing the same information repeatedly, related records are now connected through foreign key relationships.

The result is a cleaner database that is easier to maintain and less prone to update anomalies.

---

# 🛡️ Referential Integrity

Referential integrity was maintained throughout the implementation by carefully defining relationships between related tables.

This ensures that:

- Every foreign key references a valid parent record.
- Relationships remain consistent across the database.
- Invalid references cannot be introduced accidentally.

Maintaining referential integrity helps preserve the reliability and accuracy of the database as it grows over time.
